# Canterbury Details 1.0 release gate

This is the independent ordinary Canterbury 1940 simulation and documentation
release, not the later game integration. Its supported scope and unknown source
facts are documented in USER-GUIDE.md, MAP.md, PERFORMANCE.md and UNCERTAINTIES.md.
The final assembled map uses connected cropped OSM road geometry; all initial
source-map agents remain unplaced until explicit spatial qualification is supplied.

The gate creates a committed snapshot in a separate temporary repository, then
clones that snapshot and the exact two public/pinned local submodules into
`build/release-checkout`. Tests run there offline with no hardlinked object stores,
no sibling source imports, and no dependence on deleted web pages. The original
parent's pending source changes are not committed or discarded by this workflow.
The SDK checkpoint fix and its parent gitlink are committed as required by the plan.
The qualified source snapshot commit and source hashes are recorded explicitly;
they need not equal the user's parent HEAD before the user commits those sources.

Qualification covers source admission, core C/C++ ABI/profile guards, native
27,000/30,000 capacity/accounting, daily needs and lifecycle, ordinary occupations,
finite employment/economy/development, religious/community/civic services,
hand-carried transport, environment, causal privacy/provenance, operations,
complete checkpoint staging/failures, separate-process and Debug/Release replay,
actual assembled-map pixel equality, native input/management and measured budgets.
Original native/Bronze contract/actor/hybrid regressions run in isolated SDK copies
against the independent baseline, including committed guarded changes. The relocated
ordinary mock frontend proves the public core archive has no app main/Cocoa linkage.

Native GUI checks launch the resulting .app normally. They are not raw GUI binaries
used as command-line simulators. Presentation measurement is a separate normally
launched .app with copied technical glyphs and exact source/pixel fingerprints;
it makes no physical-display FPS or controller/assistive-device certification claim.

Reports are published locally under `content/`: per-cycle validation, the evidence
index and `cycle-40-validation.json`. No remote tag, upload or repository push is
performed. The release prepare command leaves the cloned checkout for native GUI
inspection; finalization checks its passing reports, source equality, committed
submodule pins, ordinary core consumer and presentation metrics before publishing
the local gate. Compiler artifacts remain reproducible under ignored `build/`.

Checkpoint format v1 has strict profile/ABI/content gates. Earlier source-qualified
saves can be rejected; use their original build to inspect them. This release does
not claim automatic migration, cross-architecture raw-layout portability, encrypted
checkpoints, verified historical staffing/housing, autonomous historical birth/death
rates, operational source rail or an already playable historical campaign.

## Completion conclusion

All 40 cycles and the local standalone release gate passed. The ordinary core,
native application and documentation are the handoff for the separate game phase.
Source uncertainties and unsupported portability/migration/device claims remain
as stated above. Cycle records retain their original test scope; the evidence
index identifies current qualification. Documentation reconciliation after the
release snapshot is recorded separately in the Cycle 40 report and does not
represent a new runtime implementation or a new historical-data qualification.
